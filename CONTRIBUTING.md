# Правила внесения изменений

Любое изменение считается потенциально ошибочным, кто бы его ни написал: участник команды или средство генерации кода. В `develop` и `main` попадает только то, что прошло проверки и ревью.

## 1. Ветки (GitFlow)

| Ветка | Откуда создаётся | Куда сливается | Назначение |
|---|---|---|---|
| `main` | — | — | только выпущенные версии, каждая отмечена тегом `vX.Y.Z` |
| `develop` | `main` | — | текущая разработка, сюда сливаются все функции |
| `feature/<N>-<кратко>` | `develop` | `develop` | одна задача (Issue №N) |
| `release/X.Y.Z` | `develop` | `main` и `develop` | подготовка релиза: смена версии, мелкие исправления |
| `hotfix/X.Y.Z` | `main` | `main` и `develop` | срочное исправление выпущенной версии |

Прямой `push` в `main` и `develop` запрещён: на GitHub включена защита этих веток, слияние только через Pull Request с одобрением.

## 2. Путь изменения

1. **Задача.** Создать Issue: что нужно сделать и как проверить, что сделано (критерии приёмки).
2. **Ветка.** `git switch develop && git pull`, затем `git switch -c feature/<N>-<кратко>`.
3. **Коммиты.** Небольшие и осмысленные: один коммит = одно логическое изменение.
4. **Локальная проверка.** `make verify` должен пройти без ошибок. Приложение запускается, `/health` отвечает `ok`.
5. **Pull Request** в `develop`. В описании `Closes #N`, заполненный чек-лист из шаблона.
6. **Ревью.** Второй участник читает изменения, при необходимости запускает их у себя и ставит Approve. Свой PR сам себе не одобряем.
7. **Слияние** кнопкой «Create a merge commit», ветка после слияния удаляется.

## 3. Изменение схемы базы данных

Схема БД меняется **только миграциями**: таблицы при запуске приложения не создаются.

1. Изменить модель в `app/models/`.
2. Создать миграцию: `alembic revision --autogenerate -m "что изменилось"` (виртуальное окружение должно быть активировано), переименовать файл в `NNNN_кратко.py` и проверить его глазами: autogenerate не всё видит правильно.
3. Применить: `make migrate`. Проверить и откат: `alembic downgrade -1`, затем снова `make migrate`.
4. Уже слитую в `develop` миграцию не меняют — исправление делается новой миграцией.

## 4. Сообщения коммитов

Формат: `<тип>: <что сделано>`, глагол в прошедшем времени или повелительном наклонении — главное единообразно.

| Тип | Когда |
|---|---|
| `feat` | новая функция |
| `fix` | исправление ошибки |
| `test` | тесты |
| `docs` | документация |
| `refactor` | переработка кода без изменения поведения |
| `chore` | зависимости, настройки, служебное |

Пример: `feat: проведение поступления увеличивает остатки`.

## 5. Обязательные проверки

```bash
make verify
```

Это `make quality` (ruff: стиль и статический анализ, проверка форматирования) и `make test` (pytest). Изменение, на котором `make verify` падает, в PR не отправляется.

## 6. Запрещено

- `push` напрямую в `main` и `develop`, `push --force` в общие ветки;
- коммитить `.env`, пароли, токены, ключи, журналы, локальные базы данных;
- удалять тесты, помечать их `skip`/`xfail` или ослаблять проверки в тестах, чтобы изменение прошло;
- отключать правила ruff (`# noqa`, `ignore` в `pyproject.toml`) без обоснования в описании PR;
- сливать PR без одобрения второго участника или при упавших проверках;
- менять задачу молча: если в процессе понятно, что задача другая, это фиксируется в Issue.

## 7. Критические файлы

Изменения в этих файлах обязательно перечисляются в описании PR и проверяются ревьюером отдельно:

`Makefile`, `pyproject.toml`, `requirements*.txt`, `tests/`, `.gitignore`, `.env.example`, `CONTRIBUTING.md`, `.github/`, `deploy/`, `migrations/`, `alembic.ini`.

`deploy/` — критические файлы эксплуатации: от них зависят права службы, открытые порты и доступ к БД. Изменение в них проверяется на машинах (`deploy/scripts/check.sh` проходит на обоих серверах) и не может ослаблять требования из [docs/deploy.md](docs/deploy.md#4-требования-к-эксплуатации): запуск не от root, закрытые лишние порты, отсутствие паролей в репозитории.

## 8. Приёмка изменения

PR принимается, если:

- [ ] есть связанная задача (`Closes #N`);
- [ ] `make verify` проходит;
- [ ] новая логика покрыта тестами;
- [ ] при изменении API или таблиц обновлены `docs/api.md` и `docs/schema.md`;
- [ ] новые настройки добавлены в `.env.example` и README;
- [ ] в изменениях нет секретов и локальных файлов;
- [ ] ревьюер одобрил PR.

## 9. Выпуск версии

1. `git switch develop && git pull && git switch -c release/X.Y.Z`
2. Поменять версию в `app/__init__.py`, закоммитить, `make verify`.
3. PR `release/X.Y.Z` → `main`, ревью, слияние.
4. На `main` поставить тег: `git tag -a vX.Y.Z -m "Версия X.Y.Z"` и `git push origin vX.Y.Z`.
5. Слить `main` обратно в `develop` (PR `main` → `develop`), чтобы смена версии попала в разработку.
6. Оформить GitHub Release по тегу с перечнем изменений.

Версии нумеруются по [SemVer](https://semver.org/lang/ru/): `MAJOR.MINOR.PATCH`.

## 10. Если секрет попал в репозиторий

Удаление коммита не помогает: история уже могла быть скачана. Сначала **сменить** пароль или ключ, затем удалить файл из репозитория и сообщить второму участнику.
