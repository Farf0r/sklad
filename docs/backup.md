# Резервное копирование и восстановление

## Что сохраняется

Резервная копия — один файл со всей базой: таблицы, ограничения, индексы, данные и номер версии схемы (`alembic_version`). Его делает утилита PostgreSQL `pg_dump` в формате `custom` (сжатый двоичный файл, который читает `pg_restore`).

Имя файла: `<база>_<дата>_<время>.dump`, например `sklad_2026-10-28_19-30-00.dump`. Если в ту же секунду сделать вторую копию, к имени добавится `_2`.

| Где | Каталог копий | Команды |
|---|---|---|
| на ноутбуке | `backups/` в папке проекта (`BACKUP_DIR` в `.env`) | `make backup`, `make restore` |
| на сервере `sklad-app` | `/var/backups/sklad` (`BACKUP_DIR` в `/etc/sklad/sklad.env`) | `sudo sklad-cli backup`, `sudo sklad-cli restore` |

В копии есть все данные, включая хеши паролей, поэтому каталог `backups/` и файлы `*.dump` в Git не попадают (`.gitignore`), а на сервере каталог доступен только пользователю `sklad` и root.

## Команды

```bash
make backup                                   # копия базы из .env
make restore                                  # восстановить из последней копии
make restore FILE=backups/sklad_2026-10-28_19-30-00.dump   # из указанной копии
```

Без make: `python -m app.cli backup`, `python -m app.cli restore [файл] [--yes]`.

`pg_dump` и `pg_restore` ищутся в `PATH`, а под Windows ещё и в `C:\Program Files\PostgreSQL\<версия>\bin` (установщик PostgreSQL не добавляет их в `PATH`). Версия утилит должна быть не ниже версии сервера PostgreSQL.

## Как работает восстановление

1. Команда показывает, какая база и из какого файла будет восстановлена, и ждёт ввода `yes`. Любой другой ответ отменяет восстановление.
2. Текущее состояние базы сохраняется в копию с пометкой `before-restore` — если восстановили не ту копию, можно вернуться. Такие копии не выбираются как «последняя» в `make restore`, их указывают явно через `FILE=`.
3. `pg_restore --clean --if-exists --single-transaction` удаляет таблицы базы и создаёт их заново из копии. Всё выполняется одной транзакцией: если файл повреждён или произошла ошибка, база остаётся как была.

Пароль от базы передаётся утилитам через переменную окружения `PGPASSWORD`, а не в командной строке, — так его не видно в списке процессов.

Если копия сделана на более старой версии приложения, после восстановления выполните `make migrate` (на сервере это делает `sklad-update`).

## Проверка: копия → порча данных → восстановление

1. Приложение запущено, в нём есть материалы и проведённые поступления. Сделать копию:

   ```bash
   make backup
   ```

2. Намеренно испортить данные в «SQL Shell (psql)» (база `sklad`, пользователь `sklad`):

   ```sql
   DELETE FROM receipts;                          -- удалить все поступления
   UPDATE materials SET stock = 0;                -- обнулить остатки
   ```

   В веб-интерфейсе поступлений больше нет, остатки нулевые.

3. Восстановить:

   ```bash
   make restore
   ```

   На вопрос ответить `yes`. После обновления страницы поступления и остатки снова на месте.

То же самое автоматически проверяет `tests/integration/test_backup.py` на тестовой базе: восстановление после удаления и изменения данных, после удаления целой таблицы, отказ на повреждённом файле без потери данных, отмена восстановления, ошибки «нет копий» и «утилита не найдена».

## На сервере

`sklad-update` делает копию перед применением миграций при каждом обновлении. Вручную:

```bash
sudo sklad-cli backup
sudo ls -l /var/backups/sklad
sudo systemctl stop sklad
sudo sklad-cli restore            # или путь к файлу
sudo systemctl start sklad
curl -s localhost:8000/health
```
