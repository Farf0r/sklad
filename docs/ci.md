# Непрерывная интеграция (CI)

CI выполняется в GitHub Actions: `.github/workflows/ci.yml`. Он запускает **те же команды make**, что и проверка на ноутбуке, и только если все они прошли, публикует образ приложения в GitHub Container Registry. Результаты — на вкладке **Actions** репозитория и в каждом запросе на слияние.

## 1. Когда запускается

| Событие | Что происходит |
|---|---|
| `git push` в любую ветку | все проверки; если прошли — сборка и публикация образа `sha-<коммит>` |
| создание и обновление запроса на слияние в `develop` или `main` | все проверки для результата слияния; образ не публикуется |
| изменение `develop` и `main` (слияние запроса) | как `git push`: проверки и публикация образа |
| тег выпуска `vX.Y.Z` | проверки и публикация образа с тегами `sha-<коммит>` и `X.Y.Z` |
| кнопка **Run workflow** на вкладке Actions | ручной запуск проверок |

Новый запуск для того же запроса на слияние отменяет устаревший.

## 2. Этапы

Задания выполняются параллельно, каждое на чистой виртуальной машине Ubuntu 24.04. Публикация ждёт все остальные.

| Задание | Команды | Что проверяет | Отчёты |
|---|---|---|---|
| Стиль и правила | `make rules`, `make quality` | правила проекта (нет skip, порог покрытия, анализаторы не отключены), стиль и форматирование (ruff) | `style-reports`: `ruff.json` |
| Безопасность кода | `make sast` | уязвимости в коде (bandit) | `security-reports`: `bandit.json` |
| Тесты | `make test` | unit-, API- и интеграционные тесты на отдельной тестовой базе, покрытие не ниже 95 % | `test-reports`: `junit.xml`, `coverage.xml`, `coverage/` |
| Миграции | `make migrations-check` | чистая база создаётся миграциями; все миграции откатываются и применяются снова; схема совпадает с моделями (`alembic check`); база с данными обновляется без потерь | вывод в журнале |
| Резервное копирование | `make backup-check` | копия → порча данных → восстановление; повреждённая копия не портит базу | вывод в журнале |
| Контейнерная проверка | `make container-check` | образ и контейнерное окружение ([docker.md](docker.md#9-проверка-make-container-check)) | вывод в журнале |
| Сборка образа | `make image` | образ собирается, тег `sha-<7 символов SHA>`, метка с полным SHA | — |
| Публикация образа | `docker push` | только для `push` и только если **все** задания выше прошли | ссылка на образ в сводке |

Отчёты сохраняются даже при ошибке и хранятся 90 дней: страница запуска → внизу **Artifacts**. Итоги тестов и опубликованный образ видны в сводке запуска (**Summary**).

## 3. Те же проверки, что на ноутбуке

CI не содержит собственных проверок: каждое задание вызывает цель Makefile. Поэтому результат на ноутбуке и в CI одинаковый, а изменить проверку можно только в одном месте.

```bash
make verify            # стиль, правила, SAST, тесты — перед каждым запросом на слияние
make migrations-check  # миграции на тестовой базе
make backup-check      # резервное копирование на тестовой базе
make container-check   # контейнерное окружение
make ci                # всё перечисленное и сборка образа — то же, что CI, кроме публикации
```

`make migrations-check` и `make backup-check` работают только с тестовой базой из `.env.test` (имя `*_test`) и удаляют в ней данные, как и тесты. Рабочая база из `.env` не затрагивается.

## 4. Тестовая база в CI

Для заданий «Тесты», «Миграции» и «Резервное копирование» GitHub Actions запускает отдельный контейнер PostgreSQL — тот же образ `postgres:17.11-trixie@sha256:…`, что в `compose.yaml`, с базой `sklad_test`. После задания он удаляется: данные разных запусков и заданий не пересекаются. Клиент PostgreSQL 17 (`pg_dump`, `pg_restore`) ставится из репозитория apt.postgresql.org: он должен быть не старше сервера.

## 5. Секреты

Пароли и ключи не хранятся ни в репозитории, ни в `ci.yml`. Они заданы в **Settings → Secrets and variables → Actions → Repository secrets**; GitHub подставляет их в задания и скрывает в журналах (`***`).

| Секрет | Для чего |
|---|---|
| `CI_DB_PASSWORD` | пароль пользователя `sklad` в тестовой базе CI |
| `CI_SECRET_KEY` | `SECRET_KEY` приложения в CI |
| `CI_POSTGRES_PASSWORD` | пароль `postgres` в контейнере `db` для `make container-check` |
| `CI_SKLAD_DB_PASSWORD` | пароль `sklad` в контейнере `db` для `make container-check` |

Значения — случайные строки из латинских букв и цифр (они подставляются в строку подключения). Сгенерировать: `python -c "import secrets; print(secrets.token_hex(16))"`. Если секретов нет, задание сразу останавливается с подсказкой.

Для публикации образа используется встроенный `GITHUB_TOKEN`: он выдаётся на время запуска, право `packages: write` есть только у задания публикации.

## 6. Кэширование

Скачанные пакеты pip кэшируются (`actions/setup-python`, `cache: pip`). Ключ кэша зависит от `requirements*.txt`: при изменении зависимостей кэш создаётся заново, иначе пакеты не скачиваются повторно.

## 7. Образ приложения

- Тег связан с коммитом: `ghcr.io/farf0r/sklad:sha-<первые 7 символов SHA>`; полный SHA записан в метку `org.opencontainers.image.revision`. Для тега выпуска добавляется тег версии, например `0.5.0`. Тег `latest` не используется.
- Публикуется **тот самый** образ, который собран в задании «Сборка образа» (он передаётся заданию публикации файлом), а не собранный заново.
- Задание публикации зависит от всех проверок (`needs`). Если хоть одна упала, публикация пропускается (**skipped**) — образ с ошибкой в реестр не попадает.

Опубликованные образы: страница репозитория → справа **Packages** → `sklad`. Скачать:

```bash
docker pull ghcr.io/farf0r/sklad:sha-1a2b3c4
```

Если пакет закрытый, перед `docker pull` нужен `docker login ghcr.io` с токеном GitHub (право `read:packages`); видимость меняется в настройках пакета (**Package settings → Change visibility**).

## 8. Если CI упал

1. Открыть запуск (крестик у коммита или вкладка **Checks** в запросе на слияние) и упавшее задание.
2. Найти первую ошибку в журнале шага `make …` — это тот же вывод, что на ноутбуке.
3. Повторить команду локально (`make test`, `make migrations-check` и т. д.), исправить, отправить коммит. CI запустится снова.

Отключать, пропускать или ослаблять проверку, чтобы CI прошёл, запрещено ([CONTRIBUTING.md](../CONTRIBUTING.md#6-запрещено)).
