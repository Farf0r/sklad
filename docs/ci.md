# Непрерывная интеграция

GitHub Actions запускает CI при отправке изменений в любую ветку, при создании и обновлении PR в `develop` и `main`, при отправке тега `v*` и вручную через **Run workflow**. Результаты видны на вкладке **Actions** и в разделе **Checks** запроса на слияние.

## 1. Проверки в Docker-in-Docker

Задания **Проверки DinD** и **Сборка и анализ образа** поднимают на своих GitHub runners отдельные контейнеры Docker-in-Docker. Каждый запускает собственный Docker daemon. В журнале есть идентификаторы внешнего и внутреннего демонов. Внутренний сокет доступен только внутри DinD и рабочему контейнеру с Python, Docker CLI и PostgreSQL 17 client. Порты наружу не пробрасываются.

| Этап | Команды и результат |
|---|---|
| Стиль и правила | `make rules`, `make tests-guard`, `make quality` |
| Безопасность кода | `make sast`, `make secrets`, `make deps` |
| Тесты | `make test`, файлы JUnit и отчёты о покрытии |
| Миграции | `make migrations-check`, применение, откат и обновление базы с данными |
| Резервное копирование | `make backup-check`, создание и проверка восстановления |
| Контейнерное окружение | `make container-check`, изолированное окружение Docker Compose |
| Сборка и образ | `make image-scan` сначала собирает образ, затем проверяет его через Trivy |
| Локальный registry | Внутри DinD запускается OCI registry на loopback. Образ отправляется, скачивается и сверяется по ID |
| Публикация | После успеха всех этапов при событии `push` тот же образ загружается в GHCR |

Тесты, миграции и резервное копирование используют контейнер PostgreSQL 17 с базой `sklad_test` внутри DinD. Этапы выполняются последовательно. Проверка Docker Compose создаёт собственное окружение и тома. Кэш pip хранится на стороне Actions и зависит от архитектуры runner, `requirements*.txt` и Dockerfile рабочей среды.

Отчёты загружаются даже при ошибке. В **Artifacts** доступны `check-reports` (ruff, Bandit, detect-secrets, pip-audit, JUnit и покрытие) и `image-reports` (Trivy). Если этап ещё не дошёл до анализатора, его отчёт отсутствует.

## 2. Пароли и публикация

Пароли тестовой БД и Compose, а также ключ приложения генерируются заново для каждого запуска, маскируются в журналах и сохраняются в игнорируемых файлах `.env` и `.env.test` на одноразовом runner. Для тестов из форков не нужен доступ к секретам репозитория. Для GHCR используется встроенный `GITHUB_TOKEN` с правом `packages: write` только в задании публикации.

Образ в GHCR получает тег `sha-<первые 7 символов SHA>`, полный SHA записан в метку `org.opencontainers.image.revision`. Для тега выпуска `vX.Y.Z` добавляется тег `X.Y.Z`. Задание публикации загружает архив проверенного образа и отправляет его в GHCR. При падении обязательной проверки задача публикации получает статус **Skipped**.

## 3. Проверки на ноутбуке

```bash
make verify
make deps
make migrations-check
make backup-check
make container-check
make image-scan
```

`make ci` запускает эти команды одной целью. Для проверки миграций, резервного копирования и приложения используется только тестовая база, данные в ней пересоздаются. `make tests-guard` сравнивает тестовые файлы и функции с `HEAD`; для сравнения всей ветки выполните `make tests-guard TESTS_BASE=origin/develop`. CI сравнивает с базовым коммитом PR или с предыдущим коммитом ветки при push.

- `make secrets` проверяет отслеживаемые файлы и новые файлы, которые видит Git. В отчёт попадают путь, строка и тип находки. Для одного вручную проверенного ложного срабатывания используйте `make secrets-baseline FILE=путь LINE=номер` и объясните исключение в PR.
- `make deps` сверяет версии из `requirements-lock.txt` и установленного окружения с базой уязвимостей PyPI. Неизвестный результат, ошибка сканирования или найденная уязвимость блокируют этап.
- `make image-scan` проверяет собранный образ Trivy, закреплённым по версии и digest. Уязвимости HIGH и CRITICAL с доступным исправлением блокируют проверку. Полный отчёт сохраняет остальные находки.

## 4. Обязательное ревью и статусы

В репозитории активен ruleset `protect` для `main` и `develop`. После первого прогона новой схемы в **Settings → Rules → Rulesets → protect** включите требование одобрения CODEOWNERS и устаревание прежних одобрений при новых коммитах. Сохраните одно обязательное одобрение. Добавьте статусы **Проверки DinD** и **Сборка и анализ образа** с источником **GitHub Actions** и включите проверку актуальности относительно целевой ветки.

GitHub читает CODEOWNERS из целевой ветки PR. Первый PR с новым файлом проходит по существующему правилу одного одобрения. После его слияния в `develop` и переноса в `main` правило CODEOWNERS применяется на обеих ветках. Владелец кода должен иметь доступ на запись. Если PR открыл Денис, ревью делает Иван. Если PR открыл Иван, ревью делает Денис.

## 5. Демонстрация на защите

1. Откройте успешный запуск для корректного коммита. Покажите этапы, два разных ID Docker daemon, артефакты и опубликованный тег для push.
2. В отдельной демонстрационной ветке измените ожидание одного существующего теста на заведомо неверное. Покажите ошибку в **Тесты** и **Skipped** у публикации.
3. Для демонстрации `make secrets` используйте искусственную строку без реального токена. Сборка должна остановиться на шаге **Безопасность кода**.
4. Проверьте барьеры по одному: уберите функцию теста, пропустите обязательную команду в workflow, снизьте порог покрытия. Сохраните журнал отказа для каждого случая. Верните демонстрационные файлы в исходное состояние.
5. Откройте PR, меняющий критический файл. Покажите требуемые статусы, запрос ревью CODEOWNERS и недоступную кнопку слияния до одобрения. Ссылки и снимки сохраните в отчёте команды.
